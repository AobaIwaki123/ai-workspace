# システム設計・OSSロードマップレビュー観点 (System Design Review Rules)

本ルールは、AIエージェントが新しいプロジェクト（OSSツール、CLI、Webサービス等）のアーキテクチャ設計や開発ロードマップを策定・レビューする際に、**ベテランエンジニアの視点から必ず確認・指摘すべき観点**を定義します。

新規プロジェクトの立ち上げ時や `/goal` コマンドでロードマップのレビューを求められた場合は、以下のチェックリストを適用してフィードバックを行ってください。

---

## 🔍 設計レビュー・チェックリスト

### 1. トレードオフと意思決定の明文化 (ADR: Architecture Decision Record)
- 採用したアーキテクチャ（例: インメモリキャッシュ vs Redis、モノリス vs マイクロサービス）には必ずメリデメが存在します。
- **Agentの振る舞い**: 設計のメリットだけでなく、「何を捨てたか（デメリット）」「なぜ現状の規模（個人開発・自作k8s等）ではそれが許容できるか」を ADR として明文化するよう促してください。

### 2. オーバーエンジニアリングの防止 (YAGNI / KISS)
- プロジェクトの規模（個人開発OSS、小規模チーム）に対して、過剰に複雑なワークフロー（例: 厳密な Git-Flow や不要に分厚いレイヤードアーキテクチャ）が提案されていないか確認します。
- **Agentの振る舞い**: 例えば、単一メンテナのOSSであれば「`main` ブランチ＋タグトリガーの自動リリース (Tag-based Release)」にシンプル化するよう提案してください。

### 3. 可観測性 (Observability) と 設定管理 (Configuration)
- 実装・デプロイされてから「ログが出ない」「ポートがハードコードされている」といった問題を防ぐ必要があります。
- **Agentの振る舞い**: ロードマップの初期フェーズ（Phase 1）に以下が組み込まれているか確認してください。
  - **構造化ロギング**（Goであれば `log/slog` など）の導入。
  - **12-Factor App** に則った環境変数ベースの設定管理。

### 4. 外部依存と非公式APIへの防衛策 (Defensive Architecture)
- 外部API（特に非公式APIやスクレイピング）は、予告なく仕様変更されるリスクが常に伴います。
- **Agentの振る舞い**: 
  - 本番相当の環境・データに対する **定期的なE2E監視 (Live Monitoring / Canary Test)** を CI/CD パイプライン（GitHub Actions Cron等）に組み込むよう提案してください。
  - 外部依存を極力 Adapter 境界に閉じ込める設計（Hexagonal Architecture 等）になっているか確認してください。

### 5. スキーマ駆動開発 (Schema-Driven / Code Gen)
- OpenAPI、GraphQL、gRPC などのスキーマを定義した場合、手動での型定義は実装の乖離（迷子）を生みます。
- **Agentの振る舞い**: スキーマファイル（例: `openapi.yaml`）を正とし、`oapi-codegen` 等を用いてコード（サーバーインターフェースや型）を **自動生成するフロー** がロードマップに明記されているか確認してください。

---

このルールに基づいてレビューを行うことで、後戻りの少ない、堅牢で保守しやすいシステム設計へと導くことができます。
