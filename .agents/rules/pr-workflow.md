# プルリクエスト (PR) 必須運用規約 (PR-Only Workflow Rule)

本ルールは、AIエージェントがコードの追加・変更・リファクタリング・ドキュメント更新を行う際の**GitおよびGitHub運用プロセス**を厳格に定義します。

---

## 🚫 1. main ブランチ直接 Push の絶対禁止

- **対象**: `ai-workspace` リポジトリおよび、作業対象となる**すべての外部・新規作成リポジトリ**（例: `lumitree` 等）。
- **原則**:
  - `main`（または `master` / `release` 等の保護ブランチ）への**直接コミットおよび直接 Push は例外なく禁止**します。
  - タイポ修正、CI修正、依存関係更新、ドキュメントの文言変更などの些細な修正であっても、必ずトピックブランチを作成してください。

---

## 🌿 2. すべての変更は Pull Request (PR) 経由

1. **ブランチの作成**:
   - 適切なプレフィックスを付けたブランチを切ります（例: `feat/*`, `fix/*`, `chore/*`, `docs/*`, `refactor/*`）。
   - 複数段階の開発を行う場合は、`stacked-pr` スキルを活用して積み上げ型 PR を作成します。
2. **Pull Request の作成**:
   - `gh pr create` を使用して GitHub 上に PR を起票します。
   - 概要、変更理由、検証内容（CI結果、単体テスト結果など）を明記します。
3. **CI の通過確認**:
   - PR を作成後、GitHub Actions CI（Lint, Test, Build）が Green（PASS）になることを確認します。

---

## 🛑 3. 勝手なマージ・クローズの禁止

- **ユーザー主権の原則**:
  - **エージェントが自律的に PR をマージしたり、クローズしたりすることは固く禁止**します。
  - 「キリのいいところまで」「実装を進めて」といった指示を受けた場合でも、**作業のゴールは「PR を作成して CI が通った状態でユーザーのレビューを待つ」こと**です。
  - マージの実行やリリース判定は、必ずユーザー自身が行うか、ユーザーからの明示的な指示（「マージしてください」等）があって初めて実行します。

---

## 🚦 4. CI が通るまで絶対にマージしない (Strict CI-Green Requirement)

- **マージ前提条件の厳格化**:
  - すべての PR は、**GitHub Actions CI の全チェック（Lint、Test、Build、Schema Drift Check 等）が 100% 成功（Green / PASS）することを確認するまで、絶対にマージ（マージの実行およびマージ依頼）を行ってはなりません**。
  - CI が `pending`（実行中）または `failure`（失敗）の状態でのマージは例外なく禁止します。
  - CI に失敗した場合は、必ず原因を調査・修正して再度 Push し、Green になることを確認してください。

---

## 📝 5. ドキュメント記述における絵文字の不使用

- README、ROADMAP、設計仕様書などの公式ドキュメントを作成・編集する際は、**原則として絵文字（emoji）を使用せず**、プロフェッショナルでクリーンなテキストスタイルを維持します。
