# プルリクエスト (PR) 必須運用規約 (PR-Only Workflow Rule)

本ルールは、AIエージェントがコードの追加・変更・リファクタリング・ドキュメント更新を行う際の**GitおよびGitHub運用プロセス**を厳格に定義します。

---

## 1. Pull Request (PR) 経由で反映する目的

- **変更単位の明確化とトレーサビリティ**:
  `main` への直接 Push を禁止し、すべての変更を Pull Request 経由とする本質的な理由は、**変更の単位（チェンジセット）を明確にし、履歴や目的・背景を追いやすくするため**です。
- **レビューと安全性の確保**:
  PR を通じて差分を一元管理することで、変更内容の検証（CI結果や動作確認）の可視化と迅速なロールバックを担保します。

---

## 2. 本リポジトリ（ai-workspace）におけるブランチ運用

### main 未コミット保持・指示時のみPR作成方式 (Main-First Workflow)
- **手元ではブランチを切らず、ユーザーが「PRを作成してください」と指示するまで main 上で未コミットのまま保持する**:
  - **背景・理由**: 手元（ローカルマシン）で複数の AI セッションやターミナルセッションを同時並行で走らせる際、作業開始時や作業途中にブランチを切り替えたり細かくコミットしてしまうと、他セッションの作業ツリーや作業中ファイルとの衝突・不整合が発生し非常に不便であるためです。
  - **自律的コミット・PR起票の絶対禁止**:
    - **エージェントが自己判断で勝手にトピックブランチを作成したり、コミットしたり、PRを起票することは固く禁止します**。
    - ファイルの作成、調査、ドキュメント追記、リファクタリング等の作業は、常に `main` ブランチ上の「未コミット（作業ツリー上の差分）」のまま保持し、チャット上でユーザーに確認・報告します。
  - **実行手順**:
    1. **作業・検証（main上）**: 常に最新の `main` ブランチ上で直接ファイルの作成・調査・編集・検証を進め、未コミットのまま保持します。
    2. **PR作成指示の待機**: ユーザーから「PRを作成してください」「PR起票をお願いします」などの**明示的な指示があるまで、絶対にコミットやブランチ切り出しを行いません**。
    3. **ブランチ作成・反映（指示受領時のみ）**: ユーザーの指示を受けて初めてトピックブランチ（例: `git switch -c <topic-branch>`）を作成し、対象ファイルをコミットしてリモートに Push します。
    4. **PR 起票**: `gh pr create` を使用して PR を起票します。
    5. **手元の即時復帰**: PR 作成後は、手元のブランチを直ちに `main`（`git switch main`）に戻し、次タスクや他セッションとの並行作業に影響を与えないようにします。

※外部の新規作成リポジトリや独立したコードリポジトリ（例: `lumitree` 等）において、独立したブランチや Worktree での開発が明確に求められる場合を除き、`ai-workspace` 内では上記「Main-First（未コミット保持）」運用を徹底します。ただし、**Discord 等のリモートチャット経由で実装指示を受けて作業する場合は、複数セッションの干渉防止のため常に Git Worktree を作成して作業します**。

---

## 3. main ブランチ直接 Push の絶対禁止

- **対象**: `ai-workspace` リポジトリおよび、作業対象となる**すべての外部・新規作成リポジトリ**。
- **原則**:
  - `main`（または `master` / `release` 等の保護ブランチ）への**直接コミットおよび直接 Push は例外なく禁止**します。
  - タイポ修正、CI修正、依存関係更新、ドキュメントの文言変更などの些細な修正であっても、必ず反映用のトピックブランチを作成して PR を経由してください。

---

## 4. Pull Request の作成と品質基準

1. **ブランチの命名**:
   - 適切なプレフィックスを付けたブランチを切ります（例: `feat/*`, `fix/*`, `chore/*`, `docs/*`, `refactor/*`）。
   - 複数段階の開発を行う場合は、`stacked-pr` スキルを活用して積み上げ型 PR を作成します。
2. **Pull Request の起票**:
   - `gh pr create` を使用して GitHub 上に PR を起票します。
   - **PR タイトルは、リリースノートだけを見て何をやったかが一目で分かるように、具体的かつ明瞭な日本語で記述します**（例: `feat: release ブランチ連動の Kubernetes 自動デプロイと検証スクリプトの追加`, `fix: .gitignore の修正による cmd/lumitree のコミット漏れ解消`）。
   - 概要、変更理由、検証内容（CI結果、単体テスト結果など）を本文に明記します。
3. **CI の通過確認**:
   - PR を作成後、GitHub Actions CI（Lint, Test, Build）が Green（PASS）になることを確認します。

---

## 5. 勝手なマージ・クローズの禁止

- **ユーザー主権の原則**:
  - **エージェントが自律的に PR をマージしたり、クローズしたりすることは固く禁止**します。
  - 「キリのいいところまで」「実装を進めて」といった指示を受けた場合でも、**作業のゴールは「PR を作成して CI が通った状態でユーザーのレビューを待つ」こと**です。
  - マージの実行やリリース判定は、必ずユーザー自身が行うか、ユーザーからの明示的な指示（「マージしてください」等）があって初めて実行します。

---

## 6. CI が通るまで絶対にマージしない (Strict CI-Green Requirement)

- **マージ前提条件の厳格化**:
  - すべての PR は、**GitHub Actions CI の全チェック（Lint、Test、Build、Schema Drift Check 等）が 100% 成功（Green / PASS）することを確認するまで、絶対にマージ（マージの実行およびマージ依頼）を行ってはなりません**。
  - CI が `pending`（実行中）または `failure`（失敗）の状態でのマージは例外なく禁止します。
  - CI に失敗した場合は、必ず原因を調査・修正して再度 Push し、Green になることを確認してください。

---

## 7. ドキュメント記述における絵文字の不使用

- README、ROADMAP、設計仕様書などの公式ドキュメントを作成・編集する際は、**原則として絵文字（emoji）を使用せず**、プロフェッショナルでクリーンなテキストスタイルを維持します。

---

## 8. Pull Request の単一責務の原則 (Single Responsibility PR)

- **1 PR = 1 つの明確な責務**:
  - 各 Pull Request は、**単一の明確な目的・責務（例: バグ修正、新機能、リファクタリング、テスト追加、ドキュメント更新、CI/CD設定等）に限定**します。
  - 「バグ修正のついでにドキュメントやテストを大きく書き換える」「機能追加のPRに無関係な依存関係の更新を混ぜる」等の**責務混在PRは禁止**します。
  - テストの追加やドキュメントの修正であっても、主目的と独立したものは別 PR として起票します。
  - **メリット**: レビュアーの負荷軽減（Small & Focused PR）、変更履歴・リリースノートの透明性向上、問題発生時の安全かつ迅速なロールバックを担保します。
