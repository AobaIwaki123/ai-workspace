# 人間に対する信頼性・透明性担保の設計原則 (Human-Centric Transparency & Verifiability)

本リポジトリにおいて、AIエージェントがUI、ダッシュボード、APIツール、計測スクリプト等を開発・改善する際は、**人間（開発者・レビュアー）が「本当に裏で本物の処理が動いているのか？」「モックではないか？」という不信感を抱かないよう**、以下の4原則を必ず遵守します。

---

## 1. 🔬 生データ・ヘッダの透過性 (Raw Transparency)
- **原則**: 装飾されたリッチな見た目だけに依存せず、生データ（Raw Data）へのアクセスを常に提供する。
- **実装要件**:
  - HTTP ステータスコード（`200 OK`, `500 Internal Server Error` 等）を明示する。
  - クライアント往復レイテンシ（RTT）やサーバー処理時間（`X-Runtime` / `apptime`）をミリ秒単位で表示する。
  - レスポンスヘッダ（`Content-Type`, `Content-Length` 等）および生レスポンスボディ（整形済み JSON / プレーンテキスト）を折りたたみや専用エリアで確認できるようにする。

---

## 2. ⚡ UIパラメータと内部実行ロジックの完全一致 (Parameter Synchronicity)
- **原則**: 画面上の入力フォームと内部で実行される処理パラメータが矛盾・乖離しない。
- **実装要件**:
  - 「測定モード（単発/パルス/高負荷）」と「並行度」「総リクエスト数」などの連動項目は、プリセット選択時に自動で同期させる。
  - 内部で `Math.min()` 等でフォールバックする場合でも、画面上の表示をそのまま放置せず、実際に実行される数値を画面上に反映する。
  - ユーザーが手動で数値を編集した場合は、自動的に「カスタム」モードに切り替えるなど、操作の意図が直感的に伝わるUIにする。

---

## 3. 🖥️ バックエンド実ログとの接続性・検証可能性 (Backend Verifiability)
- **原則**: 画面操作が本物のサーバーに届いていることを、ターミナル等の外部ツールから人間が独立して検証できる状態を作る。
- **実装要件**:
  - バックエンド（Go アプリケーション、API サーバー等）には、リクエスト受信時に標準出力へログ（メソッド、パス、処理時間、リモートIP）を出力するロギングミドルウェアを必ず仕込む。
  - UI 画面上やドキュメントに、**「ターミナルから実ログをリアルタイム監視するコマンド（例: `kubectl logs -f`, `docker compose logs -f`）」** を明記し、ワンクリックでコピーできるようにする。

---

## 4. 🐬 内部構造とボトルネックの可視化 (Internal Insight)
- **原則**: なぜその処理に時間がかかっているのか、裏側の挙動をエンジニア視点で解説する。
- **実装要件**:
  - 発行された SQL クエリの構造、ループクエリ（N+1）の回数、フルスキャン行数、CPU 負荷要因（正規表現コンパイルループ等）を透過的に解説・可視化する。
  - 必要に応じてプロファイラ（`pprof`、`alp`、スロークエリログ）への直リンクや採取コマンドを提供する。
