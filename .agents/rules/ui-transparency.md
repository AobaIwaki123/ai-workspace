# 人間に対する信頼性・透明性担保の設計原則 (Human-Centric Transparency & Verifiability)

本リポジトリにおいて、AIエージェントがUI、ダッシュボード、APIツール、計測スクリプト等を開発・改善する際は、**人間（開発者・レビュアー）が「本当に裏で本物の処理が動いているのか？」「モックではないか？」という不信感を抱かないよう**、以下の5原則および検証チェックリストを必ず遵守します。

---

## 1. 生データ・ヘッダの透過性 (Raw Transparency)
- **原則**: 装飾されたリッチな見た目だけに依存せず、生データ（Raw Data）へのアクセスを常に提供する。
- **実装要件**:
  - HTTP ステータスコード（`200 OK`, `500 Internal Server Error` 等）を明示する。
  - クライアント往復レイテンシ（RTT）やサーバー処理時間（`X-Runtime` / `apptime`）をミリ秒単位で表示する。
  - レスポンスヘッダ（`Content-Type`, `Content-Length` 等）および生レスポンスボディ（整形済み JSON / プレーンテキスト）を折りたたみや専用エリアで確認できるようにする。

---

## 2. UIパラメータと内部実行ロジックの完全一致 (Parameter Synchronicity)
- **原則**: 画面上の入力フォームと内部で実行される処理パラメータが矛盾・乖離しない。
- **実装要件**:
  - 「測定モード（単発/パルス/高負荷）」と「並行度」「総リクエスト数」などの連動項目は、プリセット選択時に自動で同期させる。
  - 内部で `Math.min()` 等でフォールバックする場合でも、画面上の表示をそのまま放置せず、実際に実行される数値を画面上に反映する。
  - ユーザーが手動で数値を編集した場合は、自動的に「カスタム」モードに切り替えるなど、操作の意図が直感的に伝わるUIにする。

---

## 3. バックエンド実ログとの接続性・検証可能性 (Backend Verifiability)
- **原則**: 画面操作が本物のサーバーに届いていることを、ターミナル等の外部ツールから人間が独立して検証できる状態を作る。
- **実装要件**:
  - バックエンド（Go アプリケーション、API サーバー等）には、リクエスト受信時に標準出力へログ（メソッド、パス、処理時間、リモートIP）を出力するロギングミドルウェアを必ず仕込む。
  - UI 画面上やドキュメントに、**「ターミナルから実ログをリアルタイム監視するコマンド（例: `kubectl logs -f`, `docker compose logs -f`）」** を明記し、ワンクリックでコピーできるようにする。

---

## 4. 内部構造とボトルネックの可視化 (Internal Insight)
- **原則**: なぜその処理に時間がかかっているのか、裏側の挙動をエンジニア視点で解説する。
- **実装要件**:
  - 発行された SQL クエリの構造、ループクエリ（N+1）の回数、フルスキャン行数、CPU 負荷要因（正規表現コンパイルループ等）を透過的に解説・可視化する。
  - 必要に応じてプロファイラ（`pprof`、`alp`、スロークエリログ）への直リンクや採取コマンドを提供する。

---

## 5. 状態循環と副作用の完全同期 (Closed-Loop State Synchronicity)
- **原則**: 画面から発火した処理（外部API呼び出し・非同期実行・AIパース等）の完了結果は、単なる一時レスポンスの画面表示で終わらせず、バックエンドの状態管理（ストア・メトリクス・永続化ファイル）に漏れなく書き戻し、UI全体を最新状態に再同期する。
- **実装要件**:
  - **プロキシの副作用閉包 (Side-Effect Closure)**: 外部API（Cloud Run、LLM、Webhook等）をプロキシ実行するエンドポイントは、呼び出し成功時に内部データストア（インメモリ一覧、ステートファイル、Prometheus メトリクス）を必ず更新・永続化する。
  - **クライアント再描画の自動同期 (Auto-Refresh Synchronicity)**: 画面上のトリガー操作が完了した際は、手動リロード（F5）を強いることなく、関連する一覧・集計・ステータスバッジをクライアント側で即座に再取得（自動リフレッシュ）して最新状態に同期する。
  - **コールドスタート・アイドル耐性 (Zero-State & Idle Snapshot)**: バックグラウンド処理がアイドル状態であっても、直近の確定スナップショット（LastRun）や同梱データを常時表示し、画面が空（0件）になる認知的な欠落を防ぐ。

---

## 実装・検証チェックリスト (Closed-Loop State Checklist)

UIやダッシュボードに新しいトリガー操作や外部呼び出しを追加する際は、以下のチェックリストをすべて満たしていることを確認します。

- [ ] **1. 副作用の閉包性 (Side-Effect Closure)**:
  - 外部APIや外部サービスの呼び出し結果は、単にブラウザへ中継（プロキシ）して終わりになっていないか？
  - 成功時にサーバー側の内部ストア（リスト、カウンタ、状態ファイル）が適切に更新・永続化されているか？
- [ ] **2. UIと状態の即時同期 (UI Synchronicity)**:
  - 操作完了直後に、関連する一覧やメトリクスがクライアント側で自動的に再取得（リフレッシュ）されているか？
  - ユーザーがリロードしなくても、成功ステータス（バッジや抽出結果）が即時視認できるか？
- [ ] **3. コールドスタート・アイドル時の可視性 (Zero-State Visibility)**:
  - コンテナ起動直後やジョブが実行されていない待機状態でも、直近の実行結果や履歴が欠落せず表示されるか？
  - 必要な静的アセットやデータディレクトリ（`data/raw` 等）が `.dockerignore` や環境分離によって意図せず除外されていないか？
- [ ] **4. 状態変更のテスト網羅 (State Mutation Testing)**:
  - 単に「APIが 200 OK を返すか」だけでなく、「API呼び出し後に内部状態・カウンタ・ファイルが期待通りに更新されたか」を検証するテストが実装されているか？
