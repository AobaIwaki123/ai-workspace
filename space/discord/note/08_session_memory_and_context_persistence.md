# セッション記憶の持続性メカニズム (独立プロセスで記憶が維持される理由)

本ドキュメントは、Discord Bot から起動される Antigravity CLI (`agy`) が、プロセスとしては完全に独立して毎回新しく生成されているにもかかわらず、「なぜ直近の会話や文脈の記憶があるのか」という疑問に対し、その内部アーキテクチャと記憶保持メカニズムを技術的に解明・記録したノートです。

---

## 1. 結論（3 つの記憶保持メカニズム）

プロセス（PID）自体はリクエストごとに別々に立ち上がっているものの、以下の **3 つのレイヤーでコンテキストが永続化・共有** されているため、エージェントは「直前の記憶がある」状態で振る舞うことができます。

| レイヤー | 記憶の保管場所 | メカニズム・役割 |
| :--- | :--- | :--- |
| **① プロジェクト会話サマリーDB** | `~/.gemini/antigravity-cli/conversation_summaries.db` | `agy` は起動時、カレントディレクトリ（リポジトリ）に紐づく「直前の会話履歴の要約」を SQLite DB から自動読み出し、プロンプトの前提コンテキストとして暗黙的に注入する。 |
| **② 作業ツリーの物理的変化** | ローカルファイルシステム (`/Users/aobaiwaki/ai-workspace`) | 前のタスクでエージェントが生成・編集したファイル（ノートやコード、Git コミット）がそのまま残っており、新プロセスが起動時にこれらを直接認識する（外部記憶としてのファイルシステム）。 |
| **③ 暗黙のセッション継続 (Implicit Context)** | `~/.gemini/antigravity-cli/conversations/` | 明示的に `--new-project` や会話完全隔離を指定しない場合、CLI は同一ワークスペースでの最近のコンテキストを引き継ぐよう設計されている。 |

---

## 2. メカニズム詳細

### 2.1 会話サマリーデータベース (`conversation_summaries.db`)
Antigravity CLI は、ローカルマシン上の `~/.gemini/antigravity-cli/` 配下に SQLite データベース (`conversation_summaries.db`) を保持しています。
- タスクが終了するたびに、そのセッションで議論された重要事項や決定事項が要約（Summary）として DB に自動記録されます。
- 次に別の `agy` プロセスが同じディレクトリで起動した際、この DB から直近のサマリーを自動取得し、LLM への初期プロンプト（システムコンテキスト）に付与します。
- これにより、「プロセスは死んでも、プロジェクトの記憶は死なない」アーキテクチャが実現されています。

### 2.2 作業ツリーそのものが「外部記憶 (Working Memory)」として機能
エージェントは、一般的なチャットボット（ステートレスな LLM API）と異なり、**手元のファイルシステムにアクセスできる自律エージェント** です。
- 1 つ目の指示で `space/discord/bot/index.js` を作成した場合、そのファイルは物理的にディスク上に存在します。
- 2 つ目の指示で立ち上がった別の `agy` プロセスは、起動直後に `git status` やディレクトリ構成を走査できるため、「さっき自分が作ったファイル」を自明の前提として認識できます。

---

## 3. 完全隔離（ステートレス）にしたい場合の方法

もし過去の会話サマリーや記憶を一切引き継がず、完全に独立・無垢な状態（クリーンな 1 ターン）で実行したい場合は、以下のオプションを付与します:

1. **`--new-project` フラグの付与**:
   - 既存のプロジェクトコンテキストをリセットし、初期状態でセッションを開始します。
2. **一時ディレクトリ (`tmpfs` や Git Worktree) での実行**:
   - 物理ファイル自体の影響を排除したい場合、独立したディレクトリでプロセスを実行します。
