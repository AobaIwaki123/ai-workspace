# レガシーシステムと決定的な差をつける差別化設計観点 (09_differentiating_architectural_advantages.md)

本ドキュメントは、旧システム（`sakamichi-penlight-quiz`）の単なる焼き直しにとどまらず、**ユーザー体験、運用性、信頼性において圧倒的な差を生み出すための 5 つのアーキテクチャ設計観点** をまとめたものです。

---

## 1. ライブ会場での完全動作を保証する「Local-First / PWA オフライン耐性」

### 旧システムの致命的弱点
クイズ出題や採点のたびにサーバー通信を行っていたため、**アイドルの大型ライブ会場（東京ドーム、代々木第一体育館、さいたまスーパーアリーナ等の数万人規模の電波飽和エリア）において通信タイムアウトが発生し、開演直前の待機列で遊べない** というファンアプリとして最大の機会損失が発生していました。

### 新アーキテクチャの設計
- **Local-First & PWA (Service Worker)**:
  - メンバー情報・カラーマスタ・軽量 WebP 画像をクライアントの `CacheStorage` / `IndexedDB` に初回プリフェッチ。
  - クイズの出題ロジック・ダミー選択肢生成・正誤判定をクライアント側の純粋関数（Pure Helper）で完結可能にする。
  - **会場でスマートフォンの電波が圏外（No Service）であっても 100% クイズが遊べる**。
- **Background Sync**:
  - オフライン中の回答ログ（`ans_<uuidv7>`）は IndexedDB にキューイングされ、終演後や移動中に通信が回復したタイミングでバックグラウンド自動同期。

---

## 2. 画像アセットの「永久不変キャッシュ (Immutable Caching)」とゼロパージ

### 旧システムの弱点
- `images/members/kousaka-marino.jpg` のような自然キーによるパス構成だったため、写真差し替え時にブラウザや CDN に古いキャッシュが残り続けた。
- 更新のたびに CDN のキャッシュパージを実行するか、URL に `?v=2` 等のクエリパラメータを手動付与する運用負荷が発生していた。

### 新アーキテクチャの設計
- **ID 連動不変ファイル名**:
  - 写真ファイル名は常にサロゲートキー連動の `mem_<uuidv7>.webp`。
  - 写真を更新する際は、新しい UUID v7 を発行して新規ファイルとして保存し、メンバーレコードの `ImageKey` を差し替える。
- **永久キャッシュヘッダーの強制**:
  - `Cache-Control: public, max-age=31536000, immutable`
  - ブラウザおよび Cloudflare CDN で 1 年間キャッシュされ、再検証リクエスト（304 Not Modified）の通信すら発生しない。CDN パージ作業は永久に不要。
- **自動最適化パイプライン**:
  - バックエンドでのアップロード時に、自動で WebP 変換、アスペクト比統一、最大幅 400px リサイズを実施（ファイルサイズを 1 枚あたり 15〜30KB に極小化）。

## 3. インテリジェント出題アルゴリズム（類似色ひっかけ & 忘却曲線復習）

### 旧システムの弱点
- 選択肢が完全ランダムだったため、「スカイブルー × パステルブルー」の正解に対して、選択肢に「赤 × 黄色」などの全く関係ない色ばかりが並び、クイズとしての難易度・面白さにムラがあった。

### 新アーキテクチャの設計
- **色差式（CIELAB $\Delta E$）に基づく「絶妙なダミー色選定」**:
  - ペンライトカラーの HEX から Lab 色空間へ変換し、正解色との「色差（Color Difference）」が近いカラーを持つメンバーを優先してダミー選択肢に選定（例: 「サクラピンク」の出題に対し、「ピンク」「薄ピンク」を持つメンバーを意図的に混ぜる）。
- **間隔反復学習 (Spaced Repetition / 苦手克服モード)**:
  - 回答ログ（`ans_`）から、ユーザーが過去に間違えた問題、直近正答率の低いグループ・期生を優先してリトライ出題。
  - 単なる当て推量ではなく、「ファンの推し活・ペンライト暗記ツール」としての実用性を最大化。

---

## 4. 可観測性 (Observability) とゼロコールドスタート運用

### 旧システムの弱点
- GCP Cloud Run のコールドスタートにより、アクセスが途絶えた後の初回アクセスで 3〜5 秒のロード待ちが発生。
- BigQuery へのログ書き込みレイテンシによるレスポンス遅延。

### 新アーキテクチャの設計
- **Go 単一バイナリ常駐**:
  - メモリフットプリントは常時 15〜25MB、起動時間は 30ms。コールドスタートは一切存在しない。
  - API レスポンスタイムは中央値 1〜3ms を達成。
- **標準構造化ロギング (`log/slog`)**:
  - Go 1.21+ 標準の `log/slog` を採用し、全ログを JSON 形式で stdout に出力。
  - 外部の有償 APM なしで、k8s の標準ログ監視（Loki / Promtail 等）と即座に統合可能。
- **ヘルスチェック & メトリクス**:
  - `/healthz` (Liveness / Readiness)
  - `/metrics` (Prometheus 形式の出題数、正答率、API レイテンシ計測)

---

## 5. ライブ実用機能「サイリウム全画面エミュレーター (Penlight Simulator)」

### 新体験の提案
- クイズ機能にとどまらず、メンバー詳細画面やクイズ正解画面から **「ワンタップでスマートフォン画面全体がその 2 色のサイリウムに変化する機能」** を提供。
- 画面の左半分・右半分にそれぞれのカラーを全画面描画し、タップで左右反転や微細な明滅（ペンライトの光の揺らぎ）を再現。
- ペンライトを忘れたファンや、追加で 3〜4 本目のサイリウムが必要になったファンのための「緊急用サイリウム代替ツール」としてライブ会場で実用可能。

## 6. まとめ: レガシーと新システムの比較一覧

| 評価軸 | 旧システム (`sakamichi-penlight-quiz`) | 新システム (`penlight-v2`) |
|---|---|---|
| **会場電波耐性** | 毎問サーバー通信のため混雑会場でフリーズ | **PWA + Local-First で圏外でも 100% 動作** |
| **画像配信** | 手動リサイズ、古いキャッシュが残る問題 | **WebP 自動変換 + 永久不変キャッシュ (`immutable`)** |
| **出題品質** | 完全ランダム（難易度ばらつき大） | **色差計算（類似色ひっかけ） + 忘却曲線復習** |
| **インフラコスト** | GCP 月額費用、IAM 管理負担 | **自宅 k8s (Cloudflare Ingress) でコストゼロ** |
| **レスポンス** | Cloud Run コールドスタート (3〜5秒) | **常駐 Go 単一バイナリ (1〜3ms 返答、コールドスタート無)** |
| **実用付加価値** | クイズで遊ぶのみ | **全画面サイリウムエミュレーター、苦手分析ダッシュボード** |
