# AI エージェント実行基盤におけるコンテナ vs VM のセキュリティ分離

本ドキュメントは、自律的にコマンド実行・ファイル変更を行う AI エージェント（Antigravity CLI など）をサーバー基盤で稼働させる際、OS レベル仮想化（Docker コンテナ）とハードウェアレベル仮想化（VM / microVM）のセキュリティ境界、特権昇格リスク、および運用トレードオフをまとめた技術ノートです。

---

## 1. コンテナ vs VM の分離境界の根本的相違

| 観点 | Docker コンテナ (OS レベル仮想化) | VM (ハードウェアレベル仮想化) |
| :--- | :--- | :--- |
| **仮想化の層** | Linux カーネルの機能 (Namespaces, cgroups) | ハイパーバイザ (KVM, Apple Virtualization) |
| **カーネルの独立性** | **ホストとゲストで単一カーネルを共有** | **ゲスト OS 専用の完全独立カーネル** |
| **ブレイクアウト耐性** | カーネル脆弱性（Dirty COW 等）や特権昇格によるホスト侵害リスクが存在 | ハイパーバイザ境界により、ゲスト内で何が起きてもホストへの波及を阻止 |
| **ファイルシステムの保護** | マウントしたホストディレクトリやボリュームが直接改ざんされるリスク | 仮想ディスクイメージ（qcow2/raw）内に完全カプセル化 |

---

## 2. なぜエージェント運用には VM が適しているのか

Antigravity CLI をサーバー化する場合、`--dangerously-skip-permissions` を付与してツール実行（`run_command`, `write_to_file` 等）を自動承認します。これは実質的に**「外部から任意のシェルコマンドを実行できるエンドポイント」**となります。

### 2.1 コンテナ運用で生じるジレンマ
- **セキュリティを締めすぎると開発タスクが失敗する**:
  コンテナを `read-only rootfs` や `cap-drop=ALL` で強固に固めると、エージェントが「テスト用に新パッケージを apt install したい」「Docker コンテナを起動して結合テストを走らせたい」といった真っ当な指示を受けた際に権限不足で失敗します。
- **Docker in Docker (DinD) の難しさ**:
  コンテナ内で Docker デーモンを動かすには `--privileged` フラグが必要となり、コンテナのセキュリティ分離が事実上無効化されます。

### 2.2 VM による解決（VM 内でのフル権限解放）
- VM 内部では、エージェントに `sudo` 権限と Docker デーモン実行権限を完全に与えることができます。
- エージェントがどんなパッケージを導入しても、誤って `/etc` やルート配下を破壊しても、ホスト OS や他のサービスには一切影響が及びません。
- 物理的なマシンをもう 1 台用意したのと同等の安全性が得られます。

## 3. スナップショットと Copy-on-Write (CoW) による即時復元

VM のディスクイメージ（qcow2 や ZFS/Btrfs ボリューム）を活用することで、以下の運用ループが実現します:

1. **ゴールデンイメージの作成**:
   - `agy` インストール済み、認証トークン設定済み、基本開発ツール導入済みの初期スナップショット（Clean State）を保存。
2. **タスクの実行**:
   - クライアントからの指示でエージェントが自由に作業・ビルド・破壊。
3. **高速ロールバック**:
   - セッション終了後、CoW スナップショットを破棄して数秒でクリーンな初期状態に巻き戻し。
